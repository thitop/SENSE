# Multi-Test Calibration — แผนการทดสอบ 6 รูปแบบเพื่อหาเซนส์ที่แม่นยำ

สถานะ: **อนุมัติแล้ว** · 2026-11-16 (คำตอบของคำถามค้างอยู่ในข้อ 7)

## 1. ปัญหาของระบบตอนนี้

- Calibration ใช้แค่ **Flick** อย่างเดียว (`TaskType::Calibration` = `FlickTask` ไม่จำกัดเป้า) ประมาณ 70 นัด 7 รอบ
- สัญญาณมีแค่ Overshoot / Undershoot จาก `ShotMovementPath` แล้ว `fit_crossover` หาจุดที่สองอย่างนี้เท่ากัน
- ผลคือเซนส์ที่ "ดีที่สุดสำหรับการสะบัด" ซึ่งมักเร็วกว่าเซนส์ที่ดีสำหรับ tracking / micro / คุมรีคอยล์
- บทเรียนจาก `compute_final_recommendation`: การผสม score curve เข้าไปทำให้ผลแย่ลง **เพราะข้อมูลไม่เป็นอิสระต่อกัน** แผนนี้ออกแบบมาเพื่อเลี่ยงปัญหานั้นตรงๆ

## 2. หลักการออกแบบ (ใช้กับทุกเทส)

1. **ทุกเทสต้องให้ "สัญญาณมีทิศทาง"** — บอกได้ว่าเซนส์ *เร็วไป* หรือ *ช้าไป* ไม่ใช่แค่คะแนนดี/แย่
   สัญญาณแบบนี้ fit ด้วย logistic crossover ตัวเดิมได้ (`fit_crossover`) และได้ค่าความไม่แน่นอน (`rel_uncertainty`) มาด้วย
2. **ทุกเทสวัดที่เซนส์ชุดเดียวกัน** — ใช้ "block" ร่วมกัน: 1 block = 1 ค่าเซนส์ × เทสสั้นๆ ทุกแบบสลับกัน
   ทำให้เทียบข้ามเทสได้ และลดผลจากการเหนื่อย/การเรียนรู้ที่ไปตกอยู่กับเทสใดเทสหนึ่ง
3. **ทิ้งช่วงปรับตัว** — 2 นัดแรก (หรือ 1.5 วิแรกของ tracking) หลังเปลี่ยนเซนส์ไม่นับ เพราะยังติดกล้ามเนื้อของค่าเดิม
4. **เป้าที่ทำซ้ำได้** — ตำแหน่งเป้า / เส้นทางเป้า / แพทเทิร์นรีคอยล์ใช้ seed ต่อ block เพื่อให้ block ที่เซนส์ต่างกันมีความยากเท่ากัน
   (ระยะ flick แบ่งเป็นช่วง 10°/30°/60–90° แบบ stratified ให้ทุก block มีครบทุกช่วงในสัดส่วนเท่ากัน)
5. **ทุกอย่างวัดเป็นองศา** ไม่ใช่ mouse count — ให้ผลไม่ขึ้นกับ DPI และ FOV
6. **ทดสอบด้วยผู้เล่นจำลองก่อน** — เหมือน `simulated_shot_with_clarity` ใน `tests/sensitivity_calibration_tests.rs` ทุกเทสต้องมีโมเดลจำลองและ test ที่ยืนยันว่าหาเซนส์ที่ตั้งไว้เจอ

## 3. รายละเอียดแต่ละเทส

ตารางสรุป: อะไรบอกว่า "เร็วไป" และอะไรบอกว่า "ช้าไป"

| เทส | สัญญาณ "เร็วไป" (ต้องช้าลง) | สัญญาณ "ช้าไป" (ต้องเร็วขึ้น) | น้ำหนักเริ่มต้น |
|---|---|---|---|
| Crosshair Placement | เป้าเล็งสั่น/ลอยตอนถือรอ | ย้ายมุมช้า, ยังไปไม่ถึงตอนเป้าโผล่ | ต่ำ |
| Flicking | Overshoot | Undershoot | สูง |
| Tracking | สั่นตั้งฉากทิศเป้า, เลยเป้าตอนเป้าเลี้ยว | ตามหลังเป้า (lag) | สูง |
| Micro-Adjustment | ข้ามจุดกลางเป้าแล้วต้องดึงกลับ | ขยับทีละนิดหลายครั้งทิศเดียวกัน | สูง |
| Recoil Control | ดึงเกิน (เป้าเล็งต่ำกว่าเป้า) | ดึงไม่พอ (ลอยขึ้น) | กลาง |
| Movement & Counter-Strafing | — (วัดเซนส์ได้น้อย) | — | ใช้เป็น diagnostic |

### 3.1 Crosshair Placement

**ทำอะไร:** มีจุด "มุม" (ขอบประตู/ขอบกำแพง) วางในระดับหัวรอบห้อง เกมไฮไลต์มุมถัดไป ผู้เล่นต้องย้ายเป้าเล็งไปวางรอ แล้วเป้าจะโผล่จากขอบหลังรอสุ่ม 0.4–1.5 วิ

**วัด:**
- `placement_error_deg` — มุมระหว่างเป้าเล็งกับจุดที่เป้าโผล่ ตอนเป้าโผล่
- `reposition_time_ms` — เวลาตั้งแต่ไฮไลต์มุมใหม่จนเป้าเล็งเข้าใกล้ภายใน 2°
- `hold_jitter_deg` — RMS ของการเคลื่อนไหวเป้าเล็งระหว่างถือรอ

**สัญญาณมีทิศทาง:** แต่ละ peek ให้ผลเป็น "เร็วไป" ถ้า `hold_jitter_deg` สูงกว่าเกณฑ์ หรือ "ช้าไป" ถ้ายังไม่ถึงมุมตอนเป้าโผล่ ถ้าไม่ใช่ทั้งสองถือว่า Direct

**หมายเหตุ:** เทสนี้วัดการอ่านเกมมากกว่าเซนส์ จึงให้น้ำหนักต่ำ แต่ช่วยจับคนที่เซนส์เร็วจนถือนิ่งไม่ได้

**ต้องเพิ่ม:** mesh ขอบกำแพง/ประตูใน `geometry.rs` (ตอนนี้มีแค่ `create_room` และ `create_sphere`), เป้าที่เคลื่อนออกจากหลังขอบ

### 3.2 Flicking (ปรับจากของเดิม)

**ทำอะไร:** เหมือน `FlickTask` เดิม แต่บังคับระยะเป็น 3 ช่วง (สั้น 5–15°, กลาง 20–40°, ไกล 60–100°) สลับกันในทุก block

**วัด:** ใช้ `ShotMovementPath::pattern` เดิม + เก็บระยะเชิงมุมของแต่ละนัด

**ทำไมต้องแบ่งช่วง:** เซนส์เร็วชนะในการสะบัดไกล เซนส์ช้าชนะในการสะบัดสั้น ถ้าสุ่มระยะแบบอิสระ ความต่างของระยะระหว่าง block จะกลายเป็น noise
fit crossover แยกต่อช่วงระยะ แล้วรวมแบบ inverse-variance (ข้อ 4) ได้ข้อมูลเพิ่มว่าผู้เล่นคนนี้ "เซนส์เดียวไม่พอดีทุกระยะ" หรือเปล่า

**สิ่งที่ทำจริงในเฟส 2:**
- เป้าวางตาม *มุมจากเป้าเล็งตอนเป้าโผล่* ที่ระยะ 9 m คงที่ (ขนาดเป้าเชิงมุมคงที่) ไม่ใช่สุ่มตำแหน่งในโลก
  มุมเงย −6° ถึง +25° (ไม่จมพื้น) ถ้าเกินจะสะท้อนขึ้น/ลง (มุมเท่าเดิม) ถ้ายังเกินจะ clamp; Far เบนจากแนวนอนไม่เกิน ±15°
- เป้าแรกของแต่ละช่วง flick รอ `update` แรกก่อนค่อยโผล่ เพราะผู้เล่นอาจหันระหว่างนับถอยหลัง
- seed เดียวกัน = มุมและทิศเดียวกันทุกครั้งที่เริ่ม (รวมถึงตอน resume)
- ค่า Flick ในผลรวมยังเป็นเทสเดียว (นับรวมทุกช่วง) — การแบ่งช่วงแบบ 3/3/3 ทุก block ทำหน้าที่ลด noise แล้ว
  ส่วนค่าต่อช่วงใช้ joint fit อีกชุดที่จัดกลุ่มตามช่วง (`BlockScheduler::flick_bands()`) เพื่อแสดงผลและแจ้งเตือนเท่านั้น
- แจ้ง "ระยะสั้นกับไกลชอบเซนส์ต่างกัน" เมื่อ offset ของ Short กับ Far ต่างกันเกิน 1.96σ (เปรียบเทียบคู่เดียวที่วางแผนไว้)
  ผลจำลอง: แจ้งผิด ~2%, ช่องว่าง 2× (50 vs 25 cm) ตรวจเจอ ~83% — แต่ละช่วงมีแค่ 21 นัดต่อ session ช่องว่างที่เล็กกว่านี้จะตรวจไม่ค่อยเจอ

### 3.3 Tracking (ปรับจากของเดิม)

**ทำอะไร:** `TrackingTask` เดิม แต่ใช้เส้นทางเป้าแบบ seed (ความเร็ว 2 ระดับ, เลี้ยวทุก 0.8–1.8 วิ) ช่วงละ 8 วิต่อ block

**วัด (ทุก physics tick):** เวกเตอร์ error = ทิศเป้าเล็ง − ทิศเป้า (องศา) แยกเป็น
- `along_error` = error · v̂ (v̂ = ทิศความเร็วเป้า) → **ติดลบ = ตามหลัง (ช้าไป)**
- `cross_jitter` = RMS ของส่วนตั้งฉาก หลังกรอง high-pass ~4 Hz → **สูง = สั่น (เร็วไป)**
- `reversal_overshoot` = เลยเป้าไปทางเดิมกี่องศาใน 250 ms หลังเป้าเลี้ยว → **สูง = เร็วไป**

**สัญญาณมีทิศทาง:** ตัดเป็นหน้าต่าง 0.5 วิ แต่ละหน้าต่างให้ผล เร็วไป/ช้าไป/Direct ตามเกณฑ์ข้างบน แล้วเข้า `fit_crossover` เหมือนนัด flick
หักค่า reaction lag คงที่ (~150 ms ของการเลี้ยว) ออกก่อน ไม่งั้นทุกคนจะดู "ช้าไป"

**สิ่งที่ทำจริงในเฟส 4** (`src/sensitivity/tracking_signal.rs`, `TrackingAnalyzer`) — เปลี่ยนจากร่างข้างบน 3 จุด:
1. **โหวตด้วย along-error อย่างเดียว:** ค่าเฉลี่ยของตำแหน่งเป้าเล็งตามทิศที่เป้าเคลื่อนที่ในหน้าต่าง 0.5 วิ
   นำหน้า > deadband = เร็วไป, ตามหลัง > deadband = ช้าไป, deadband = 15% ของรัศมีเชิงมุมของเป้า (สมมาตรรอบศูนย์)
2. **jitter และ reversal overshoot ไม่โหวต** (jitter เก็บเป็น feature `cross_rms_deg` หลังลบค่าเฉลี่ยในหน้าต่าง)
   เพราะทั้งคู่โหวตได้แค่ทาง "เร็วไป" ทางเดียว → เลื่อนจุดสมดุลที่ search หา → ผลจะช้ากว่าจริงทุกคน
3. **ตัดช่วงหลังเลี้ยวทิ้งแทนการหักค่าคงที่:** ไม่นับ 0.35 วิหลังเป้าเปลี่ยนทิศหรือเด้งขอบ (~150 ms ตอบสนอง + ~200 ms ไล่ทัน)
   ค่าคงที่ต้องรู้ค่าของแต่ละคน; หน้าต่างที่นับได้ไม่ถึง 40% ไม่ให้ผล
- path แบบ seed: เส้นตรงเป็นช่วงๆ ความเร็วสลับ 2.5 / 4.5 m/s (≈16 / 29 °/s ที่ 9 m) ไม่มีการส่าย; โหมด practice ยังส่ายเหมือนเดิม
- ทดสอบด้วยผู้เล่นจำลอง (ดีเลย์การมองเห็น 120 ms, มือขยับเหมือนเซนส์ที่ชอบ) ที่บังคับ `TrackingTask` และ `Camera` ตัวจริง
  ผู้เล่นจำลองใช้ efference copy (คาดเดาข้ามดีเลย์ด้วยการหมุนที่ตัวเอง *คิด* ว่าหมุนไป) เหมือน smooth pursuit จริง
  โมเดลแรกที่ไม่มีการคาดเดา + แก้ error 8/s แกว่งจนไม่เสถียรที่เซนส์เร็ว ซึ่งเป็นปัญหาของโมเดล ไม่ใช่ของตัววิเคราะห์
- **ผลจำลอง (เทส tracking อย่างเดียว, 7 block × 8 วิ):** แก้ error แบบทั่วไป (8/s) ได้จุดสมดุล 0.95× ของเซนส์ที่ชอบ, แก้ช้า (4/s) ได้ 0.90×
  **ยังเอียงไปทางเร็วเล็กน้อย** เพราะ 0.35 วิตัดช่วงไล่ทันได้ไม่หมด อยู่ในช่วง ±10% ของ fit และในผลรวม tracking เป็น 1 ใน 5 เทส
  ไม่ได้เพิ่มเวลาตัดทิ้งเพื่อลบตัวเลขนี้ เพราะจะเป็นการปรับให้เข้ากับโมเดลของตัวเอง → ต้องตรวจกับการเล่นจริง
  (3 ค่าเซนส์ที่ทดสอบให้สัดส่วนเดียวกันเพราะโมเดลไม่ขึ้นกับสเกล จึงไม่ใช่หลักฐานอิสระ 3 ชุด)
- การจำลองเฟส 1 สมมติ tracking ให้ 16 สัญญาณต่อ block; ของจริงจะน้อยกว่าเพราะหน้าต่างหลังเลี้ยว/เด้งขอบถูกตัด → ตรวจตอนต่อเข้าเกม (เฟส 6.5)

### 3.4 Micro-Adjustment (ปรับจากของเดิม)

**ทำอะไร:** `MicroAdjustTask` เป้าขนาดหัว (รัศมี 0.16) ห่าง 1–5° จากเป้าเล็ง

**วัด:**
- `submovements` — จำนวนช่วงที่ความเร็วขึ้นแล้วลง ก่อนยิง
- `crossed_center` — ข้ามจุดกลางเป้าบนแกนหลักแล้วกลับมาหรือไม่
- `settle_time_ms`

**สัญญาณมีทิศทาง:** ข้ามจุดกลาง = เร็วไป, ≥3 submovement ทิศเดียวกันโดยไม่ข้าม = ช้าไป
ต้องมี classifier แยกจาก flick: ค่า `MIN_CLASSIFIABLE_SAMPLES` และเกณฑ์ `> 1.5` count ใน `from_samples` หยาบเกินไปสำหรับการขยับ 1–5° ที่ DPI ต่ำ → เปลี่ยนเป็นเกณฑ์องศา

**สิ่งที่ทำจริงในเฟส 3** (`src/sensitivity/micro_signal.rs`, `classify_micro`):
- ทุกเกณฑ์เป็นองศา (แปลง count ด้วย `deg_per_count(dpi, cm/360)` ของนัดนั้น) และวัด *ความคืบหน้าตามทิศไปหาเป้า* — classifier รู้ตำแหน่งเป้า ต่างจากของ flick
- **เร็วไป:** ไปเลยจุดกลางเกิน `max(0.15°, 10% ของระยะ)` แล้วกลับมาเกินระยะเดียวกัน
- **ช้าไป:** ≥3 stroke ไปทางเป้า (แต่ละ stroke ≥ 0.05°) โดยไม่มี stroke ถอยหลัง; stroke แยกด้วยความเร็วเฉลี่ย 10 ms (เริ่มที่ 15% ของ peak, จบที่ 8%) หรือช่วงหยุด > 25 ms
- **แก้ 1 ครั้งถือว่าปกติ** ไม่ว่าขนาดเท่าไร; ขยับจิ๋วๆ ท้ายสุด (ช้ากว่า 15% ของ peak) ไม่นับเป็น stroke
- features ที่เก็บ: ระยะเป้า, จำนวน stroke หน้า/หลัง, ข้ามกลางไหม, เลยไปกี่องศา, settle_ms
- ช่วงมุมเป้า **1.5–5°** (ไม่ใช่ 1–5° ตามร่างแรก): เป้าขนาดหัวรัศมี ~1° ที่ 9 m ถ้าห่าง 1° จะทับเป้าเล็งตั้งแต่โผล่
- เป้าวางด้วย `place_target` ตัวเดียวกับ flick (9 m, มุมเงย −6..25°) แทนการ clamp ในกล่องที่ทำให้มุมจริงเพี้ยน; บันทึก offset ในพิกัดเมาส์ (องศา, y ลง) ที่ทดสอบแล้วว่าหมุนกล้องตามแล้วตรงเป้า < 0.05°
- เทียบกับ classifier ของ flick บนเส้นทางเดียวกัน: ไปเลย 0.6° แล้วกลับ → ของเดิมได้ Direct ที่ 400 DPI แต่ Overshoot ที่ 3200 DPI (ขึ้นกับ DPI จริง); แก้ 2.4+0.6 ได้ Undershoot แต่ 2.0+1.0 ได้ Direct (ไม่สม่ำเสมอ) ส่วนกรณีชัดเจนทั้งสองให้ผลเหมือนกัน
- **โหมด practice เปลี่ยนด้วย:** เป้าอยู่ 9 m คงที่ (เดิม 9–12 m), เป้าถัดไปโผล่ทันทีหลังยิงโดน (เดิมรอ animation 120 ms), เป้าแรกรอ update แรก

### 3.5 Recoil Control (ใหม่)

**ทำอะไร:** กดค้างคลิกซ้ายยิงอัตโนมัติ 10 นัด/วิ, 20 นัด เป้าเล็งถูกดันขึ้นตามแพทเทิร์นกลางๆ ที่ไม่ใช่ของเกมใด (ขึ้นรวม ~7°, ส่ายข้าง ±1.5° ช่วงท้าย) ผู้เล่นต้องดึงลงให้อยู่บนเป้านิ่ง

**วัด:** `vertical_error_deg` ต่อนัด (ติดเครื่องหมาย) และ `horizontal_error_deg`
- ค่าเฉลี่ย vertical ติดลบ (ต่ำกว่าเป้า) / แกว่งข้ามขึ้นลง = **ดึงเกิน = เร็วไป**
- ค่าเฉลี่ยติดบวก (ลอยขึ้น) = **ดึงไม่พอ = ช้าไป**

**ทำไมเป็นสัญญาณที่ดี:** แพทเทิร์นกำหนดเป็นองศา ระยะเมาส์ที่ต้องดึงจึงแปรตาม cm/360 ตรงๆ เป็นสัญญาณที่ "สะอาด" ที่สุดในทั้ง 6 เทส
แต่คนที่ไม่เคยคุมรีคอยล์จะดึงไม่พอเสมอไม่ว่าเซนส์ไหน → ต้องมี 2 สเปรย์ฝึกก่อนเริ่ม และถ้า fit แล้วไม่มี crossover (`b >= 0`) ให้ตัดเทสนี้ทิ้งจากผลรวม

**ต้องเพิ่ม:** `InputState` ตอนนี้ส่งแค่ edge ของการกด (`set_left_mouse`) → ต้องเปิดสถานะ "กดค้าง" ให้ task, เพิ่ม `Task::on_fire_held` หรือส่งสถานะปุ่มใน `update`, และ camera offset จากรีคอยล์ที่แยกจาก yaw/pitch ของผู้เล่น

### 3.6 Movement & Counter-Strafing (ใหม่)

**ทำอะไร:** เพิ่มการเดิน WASD (เร่ง/หน่วงแบบเกม tactical) ปืนแม่นเฉพาะตอนความเร็ว < 34% ของความเร็วสูงสุด เป้าโผล่ระหว่างที่ผู้เล่นสเตรฟ ต้องกดทิศตรงข้ามเพื่อหยุดแล้วยิง

**วัด:**
- `counter_strafe_ms` — เวลาตั้งแต่ปล่อยปุ่มจนหยุดได้, ยิงก่อนหยุด (นัดที่ไม่แม่น)
- `moving_aim_error_deg` — error ของเป้าเล็งระหว่างเดิน (ต้องหมุนชดเชยการเคลื่อนที่ของตัวเอง)

**ข้อสังเกตตรงๆ:** การ counter-strafe เป็นเรื่องจังหวะคีย์บอร์ด **แทบไม่บอกอะไรเกี่ยวกับเซนส์**
ส่วนที่เกี่ยว (เล็งตามขณะเดิน) ซ้ำกับ Tracking **ตัดสินแล้ว: เทสนี้เป็น diagnostic อย่างเดียว ไม่นับรวมในค่าเซนส์** (`k = 0`) แสดงผลเช่น "คุณยิงก่อนหยุด 40% ของนัด"
ไม่อยู่ใน block ของ calibration (เพื่อให้ session คงที่ ~10 นาที) แต่เป็นเทสแยกที่เล่นได้จากหน้า Practice
และทำเป็นเฟสสุดท้าย เพราะต้องเพิ่มระบบเดิน, collision กับห้อง, และ keyboard state ทั้งหมด (`Camera` ตอนนี้ตำแหน่งคงที่)

## 4. การรวมผลเป็นค่าเดียว

1. **Joint fit** (`src/sensitivity/joint_fit.rs`, เปลี่ยนจากร่างแรกในเฟส 1): fit logistic ครั้งเดียวบนทุกเทส
   `P(เร็วไป | พลาด) = σ(c + d_i + b·(ln cm − mean))` — slope `b` ร่วมกัน, offset `d_i` ต่อเทส ถูกดึงเข้าหากันเบาๆ (ridge λ = 0.25)
   ได้ `ln c_i = mean − (c + d_i)/b` ต่อเทส พร้อม covariance ระหว่างเทส
   *ทำไมไม่ fit แยกต่อเทส:* ในผู้เล่นจำลอง fit แยกล้มเหลวบ่อย (แต่ละเทสพลาดไม่กี่ครั้งต่อ block) ข้อมูลถูกทิ้ง ผลแย่พอๆ กับ flick อย่างเดียว (6.8% vs 6.9%)
2. รวมใน log-space แบบ inverse-variance:
   `σ_i = u_i / 1.96`, `w_i = k_i / σ_i²`, `ln(cm*) = Σ w_i ln(c_i) / Σ w_i`
   โดย `k_i` = น้ำหนักเริ่มต้นจากตารางข้อ 3 (สูง 1.0, กลาง 0.6, ต่ำ 0.3)
3. ความไม่แน่นอนรวม: `Var = ŵᵀ C ŵ` (ŵ = w ที่ normalize, C = covariance เต็มจาก joint fit เพราะค่าแต่ละเทสใช้พารามิเตอร์ร่วมกันจึงไม่อิสระ) → ใช้แทน `PsaCalibrator::confidence()` เดิม
4. **ตรวจความขัดแย้ง:** เทียบ offset `d_a − d_b` (เทสสองตัวเอียงต่างกันไหม *ที่เซนส์ที่ทดสอบจริง*) แทนการเทียบค่า cm
   เพราะค่า cm ของเทสที่ชอบเซนส์ไกลจากจุดทดสอบต้อง extrapolate จน σ กว้างมาก
   เกณฑ์ **2.8σ** (5 เทส = 10 คู่ ถ้าใช้ 2σ ผู้เล่นที่ทุกเทสเห็นตรงกันจะโดนแจ้งผิด ~24%)
   ผลจำลอง: แจ้งผิด ~2%, ตรวจเจอช่องว่าง 2× (25 vs 50 cm) ~93%, ช่องว่าง 1.46× (28 vs 41) แค่ ~40% — 7 block ไม่พอแยกช่องว่างเล็กกว่านั้นได้น่าเชื่อถือ
   แสดงในหน้าผลว่า "Flick ชอบ 25 cm, Tracking ชอบ 50 cm" แทนที่จะซ่อนไว้ในค่าเฉลี่ย
5. **Preset ตามเกม (เลือกได้):** ปรับ `k_i` ตามเกมหลักของโปรไฟล์ เช่น Valorant/CS2: flick+micro+placement สูง, Apex/Overwatch: tracking สูง
   **เปิดเป็นค่าเริ่มต้น** ใช้ preset ของเกมหลักในโปรไฟล์ (`primary_game_id`) ค่าที่แนะนำและบันทึกจึงเป็นค่าตาม preset
   หน้าผลแสดงค่ากลาง (`k_i` ตามตารางข้อ 3) ไว้ข้างกันเสมอ และผู้เล่นปิด preset ได้ในหน้าผล/Settings
   - เกมที่ไม่มี preset → ใช้น้ำหนักกลาง
   - เปลี่ยนเกมหลักหรือเปิด/ปิด preset → คำนวณใหม่จาก raw sample ที่เก็บไว้ (ข้อ 4.1) ไม่ต้องเล่นใหม่
   - `CalibrationResult` เก็บว่าคำนวณด้วย preset ไหน (`weight_preset: Option<String>`) เพื่อให้หน้า History บอกได้ว่าค่าเก่ามาจากน้ำหนักชุดไหน
   - preset ต้องผ่านเกณฑ์ผู้เล่นจำลองเหมือนค่ากลาง (ข้อ 6) และค่าตาม preset ห่างจากค่ากลางได้ไม่เกิน σ* ของรอบนั้น
     เพื่อให้ preset แค่เอียงผลระหว่างเทสที่ขัดกัน ไม่ใช่สร้างค่าที่ข้อมูลไม่รองรับ
6. **เก็บ raw sample ต่อเทสในโปรไฟล์** — ดูข้อ 4.1

### 4.1 การเก็บ raw sample ในโปรไฟล์

เก็บทุกตัวอย่างที่ใช้คำนวณ เพื่อให้คำนวณผลใหม่ได้เมื่อปรับ classifier/น้ำหนัก/preset โดยไม่ต้องเล่นใหม่

```rust
// src/data/calibration.rs — ฟิลด์ใหม่ทั้งหมด #[serde(default)] ให้โปรไฟล์เก่าโหลดได้
pub struct TestSample {
    pub block: u8,            // block ที่เท่าไร
    pub cm_360: f32,          // เซนส์ตอนเก็บตัวอย่าง
    pub signal: Signal,       // TooFast | TooSlow | Direct
    pub features: Vec<f32>,   // ค่าที่ใช้ตัดสิน signal (องศา/ms) เช่น flick: [ระยะ°, path_eff, correction_share]
}
pub struct TestRecord {
    pub kind: TestKind,       // Placement | Flick | Tracking | Micro | Recoil | Strafe
    pub version: u16,         // เวอร์ชัน classifier ที่สร้าง signal
    pub samples: Vec<TestSample>,
    pub crossover: Option<Crossover>,
}
// CalibrationResult += tests: Vec<TestRecord>
```

- **ไม่เก็บ** เส้นทางเมาส์ทั้งเส้น (หลายพันจุดต่อนัด) เก็บแค่ features ที่สรุปแล้ว
  ประมาณ ~250 ตัวอย่าง/session × ~40 ไบต์ JSON ≈ 10 KB ต่อ calibration
- เก็บไว้ 20 calibration ล่าสุดต่อโปรไฟล์ (≈ 200 KB) อันที่เก่ากว่านั้นลบ samples ทิ้ง เหลือแค่ crossover ต่อเทส
- `version` ทำให้รู้ว่าตัวอย่างเก่าสร้างด้วย classifier รุ่นไหน ถ้าเปลี่ยนเกณฑ์ ตัวอย่างเก่าจะคำนวณใหม่จาก `features` ได้

ทำไมไม่ซ้ำปัญหาเดิม: แต่ละเทสได้สัญญาณจากการเคลื่อนไหวคนละแบบ และทุกเทสวัดที่เซนส์ชุดเดียวกัน จึงเป็นหลักฐานที่ค่อนข้างอิสระจริง ต่างจาก score curve ที่ใช้นัดเดียวกับ PSA

## 5. ลำดับการทดสอบในหนึ่ง session

```
วอร์มอัพ (ไม่นับ, ที่เซนส์ปัจจุบัน)     ~60 วิ   flick 10 + tracking 8 วิ + recoil 2 สเปรย์
Block 1..7 (เซนส์ที่ search เลือก)       ~70 วิ/block
  ├ ทิ้ง 2 นัดปรับตัว
  ├ Flick 9 นัด (3 สั้น / 3 กลาง / 3 ไกล)
  ├ Micro 6 นัด
  ├ Tracking 8 วิ
  ├ Recoil 1 สเปรย์ (20 นัด)
  └ Placement 4 peek
  (ลำดับเทสใน block สุ่มสลับ เพื่อไม่ให้เทสไหนโดนความเหนื่อยตลอด)
ยืนยันผล (ไม่บังคับ)                     ~60 วิ   A/B แบบไม่บอก: ค่าที่ได้ vs ±10%
รวม ≈ 10 นาที
```

- **การเลือกเซนส์ของแต่ละ block:** 2 block แรกแบ่งครึ่งช่วงแบบเดิม จากนั้นใช้ crossover **รวม** (ข้อ 4) เป็นจุดทดสอบถัดไป แทนที่จะเป็นของ flick อย่างเดียว
  ทิศของ block ตัดสินด้วยโหวตถ่วงน้ำหนัก `Σ k_i·(เร็วไป − ช้าไป)/พลาด` ของแต่ละเทส
- **เล่นครบ 7 block เสมอ** ไม่หยุดเมื่อขอบเขตแคบกว่า 2 cm (ต่างจาก PSA เดิม) — ในการจำลอง block ที่ noise เยอะ block เดียวบีบช่วงจนจบหลัง 3 block ได้
  จุดทดสอบตาม fit ออกนอกขอบเขตปัจจุบันได้ 20% เผื่อขอบเขตถูกตั้งผิดฝั่งจาก block ต้นๆ
- **ช่วงค้นหา:** คงไว้ 15–80 cm/360 แต่เริ่มจากรอบค่าปัจจุบันของผู้เล่นได้ (± 40%) เพื่อลดจำนวน block
- **โหมดเร็ว:** เลือกเฉพาะเทสที่ต้องการได้ (เช่น flick+micro อย่างเดียว) ระบบรวมผลทำงานเหมือนเดิมแค่มีเทสน้อยลง

- เล่นจริงแล้ว 1 ครั้ง (ผลข้างบน); ยังไม่ได้เทียบค่ากับเซนส์จริงหรือทำ test–retest
